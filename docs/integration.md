# Social provider integration

The workflow depends on an authenticated adapter for comment and DM intake, public replies, initial private replies, and follow-up DMs. A connected Instagram professional account can support this flow with the appropriate permissions and subscriptions. A new provider must expose the same capabilities or return a clear unsupported or ineligible outcome. [Instagram Platform overview](https://developers.facebook.com/documentation/instagram-platform/overview) · [Blotato product comparison, November 2026](../evidence/2026-11-24-blotato-product-context.md)

## Instagram pricing flow

1. Normalize a new external comment on a supported standard feed post. Carry the connected account, comment, commenter, and event identities, and the comment creation time. Map the webhook's media ID to `postId`. The default account-wide scope accepts supported comments with or without that field. A version scoped to one post requires an exact media ID match. Read the comment's `timestamp` when the webhook lacks creation time. The workflow uses that time to calculate its send cutoff. The envelope timestamp can record when Meta sent the notification. [Instagram Comment reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-comment#fields) · [Instagram webhook examples](https://developers.facebook.com/documentation/instagram-platform/webhooks/examples).
2. Reply publicly to the triggering comment with `Sent you a DM!`. The workflow gives this acknowledgement the same cutoff as the private reply so an older comment cannot receive an acknowledgement when the private reply window has already elapsed. A permanent or uncertain private-send outcome can still leave the public acknowledgement visible. The per-action status exposes that partial outcome. [Instagram comment moderation](https://developers.facebook.com/documentation/instagram-platform/comment-moderation).
3. After the public reply is accepted, send the email prompt as a comment-scoped private reply using `recipient.comment_id`. Meta returns the recipient's Instagram-scoped ID and the message ID. Meta allows one initial private reply for the triggering comment. For posts and reels, send it within seven days of comment creation. Live comments have a broadcast cutoff. The initial DM may land in Message Requests. [Instagram private replies](https://developers.facebook.com/documentation/instagram-platform/private-replies).
4. After an eligible email reply, use ordinary messaging with the scoped recipient ID to send the final DM. On this path, Meta requires a recipient response and a follow-up within 24 hours of that response. Measure provider eligibility from the response's provider timestamp. The workflow's 24-hour wait instead starts at the prompt send attempt. [Instagram private replies](https://developers.facebook.com/documentation/instagram-platform/private-replies) · [Instagram Send Messages](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api).

## Reply correlation and delivery

Deduplicate each inbound DM by its message ID within the connected account. Match the account and commenter using Instagram-scoped IDs, and ignore echoes and non-message notifications. Meta can include `message.reply_to.mid` for an inline reply. Plain DMs may omit the originating message or comment ID. [Instagram webhook examples](https://developers.facebook.com/documentation/instagram-platform/webhooks/examples).

The adapter must preserve an explicit reply target from the authenticated provider event. Keep a mapping within the authorized connected account from the provider's outbound message ID to the stable action UUID sent in `id` and `Idempotency-Key`. Resolve the provider's reply target through this mapping and forward the UUID as `replyToActionId`. When the explicit target cannot be verified, forward `replyToActionId: null`. Intake records that event's identity for deduplication, so redelivery of the same message does not re-evaluate it after the mapping becomes available. The normalized API checks the action UUID against the active run's email prompt before buffering a response, retaining an excerpt, or capturing a lead. The recording adapter tests this normalized contract. Provider webhook parsing and the provider-ID mapping belong to the production integration.

Omit `replyToActionId` for a plain DM. The workflow routes it to the single eligible wait for the tenant, account, and commenter using its time window. A plain DM can still be unrelated to the prompt. The post scope applies at comment intake. Leave `postId` out of normalized DM events.

When the pinned version enables participant context, the workflow can retain redacted excerpts of the trigger and eligible replies. The provider still receives a comment-scoped private reply and requires a fresh eligible inbound reply before the workflow sends the link. [Participant context](data.md#participant-context)

The workflow stores the source timestamps and freezes an exclusive `sendBefore` value for each queued action. The public reply and initial prompt use the comment creation time plus 168 hours. The final DM uses the accepted response's provider time plus 24 hours. If a known-unsent action can no longer dispatch within that window, the worker records `window_expired` and expires the run. An uncertain send stays unresolved because it may already have reached the provider. The connector must check eligibility at the actual send, including any narrower provider limits, and route the private reply and follow-up to their respective identifiers.

Workers rotate claim turns across tenant and account queues with due work. A newly active queue joins at the tail. Each turn claims that queue's oldest due action, and workers skip locked queues and queues in cooldown. This spreads claims among eligible queues. Sends can still finish in a different order as provider latency varies.

The adapter and intake clocks must agree. Intake records and ignores an event with a provider timestamp later than its database receipt, so clock skew can cause an otherwise valid event to be skipped.

The HTTP test records provider actions and their deadlines at a simulated provider boundary. Use the stable local action ID for internal deduplication and reconcile an unknown outcome with verified provider evidence or provider-side idempotency when available. An acceptance receipt confirms provider acceptance. Delivery and read receipts require separate evidence.

## Connection permissions

The integration owns login, token lifecycle, and account authorization. For Instagram Login, the `comments` webhook requires `instagram_business_basic` and `instagram_business_manage_comments`. The `messages` webhook requires `instagram_business_basic` and `instagram_business_manage_messages`. Unified Login and Facebook Login use different scopes. Meta requires Advanced Access for comment moderation when an app serves professional accounts it does not own or manage. [Instagram webhook fields and permissions](https://developers.facebook.com/documentation/instagram-platform/webhooks/fields) · [Instagram comment moderation](https://developers.facebook.com/documentation/instagram-platform/comment-moderation).
