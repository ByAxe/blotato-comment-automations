# Where changes belong

The API and worker run in separate processes and share PostgreSQL. The provider sits across a network boundary. Giving workflow state and the outbox separate databases would turn one business decision into two independently committed writes. Keep those writes together and keep provider translation behind the adapter.

## Five changes and their cost

| Change | What has to change together | Boundary decision |
| --- | --- | --- |
| Add a sending provider | Across the network, the provider has its own identifiers, deadlines and acceptance semantics. The worker needs only a stable action ID, cutoff and an outcome it can trust. This is weak **contract coupling** at high distance if the adapter translates those facts faithfully. | Implement the transport behind `SocialAdapter`. An accepted-for-processing response needs a later terminal result before the workflow advances. Adding a different social *platform* also requires reviewing intake identity, eligibility and send windows. [Adapter](../src/adapter.ts) · [Integration contract](integration.md) |
| Scope a published trigger to one post | Publishing and matching share the meaning of a nullable post ID. This is strong **functional coupling** at short distance. Each run pins its revision. The current change touches HTTP decoding, version storage and the matcher. | Keep publishing and matching in the workflow module. Evaluate the new predicate when starting a run. Delivery still reads the pinned revision for message content. [Workflow](../src/workflow.ts) · [Migration](../db/005_post_scope.sql) · [Upgrade and pinning cases](../test/post-scope.test.ts) |
| Resolve a send whose acknowledgement was lost | Delivery settlement and the next workflow step share a business rule. Recording a receipt can enqueue the next action. Reconciliation must execute that same transition under the attempt fence. This is strong **functional coupling** kept close by one database transaction. | Keep operator evidence collection separate from settlement. Both normal and operator-confirmed sends use `settleSent`. Preserve the distinct proofs of absence and sender quiescence before requeueing. [Settlement and reconciliation](../src/delivery.ts) · [Recovery procedure](delivery-recovery.md) |
| Change fairness between accounts | Worker SQL depends directly on the lane counters, turn order and row-lock protocol. This is strong **intrusive coupling** to the scheduling schema. The trigger maintains counts for each pending-state change, including retries. | Treat the claim query, indexes and triggers as one implementation. A separate scheduler would add coordination with every enqueue and requeue. The unit of fairness is a claim for an eligible account. Completion order also depends on provider latency. [Claim implementation](../src/delivery.ts) · [Lane schema](../db/004_fair_delivery.sql) · [Fairness cases](../test/fairness.test.ts) |
| Change a funnel measure | Reporting reads operational rows directly. It depends on an implicit business rule. The view counts a `link_dm` row as a capture because `capture` writes the lead and queues the link in one transaction. A new path that captures an email without queuing a link would undercount. | Keep the SQL view for the current flow. If those business events diverge, persist a non-personal capture fact in the capture transaction and count it by the run's original UTC start cohort. A separate analytics service would still need this fact. [View](../db/003_analytics.sql) · [Capture](../src/workflow.ts) · [Erasure and late-receipt case](../test/analytics.test.ts) |

## Decisions from the review

The plugin found that the initial claim query chose one lane before trying to lock its head action. A transaction holding that action lock could make the worker report an empty queue while a quiet account had work ready. The revised query locks both the lane and its head while selecting the candidate, so PostgreSQL can skip a locked pair and select another account in the same pass. Only a successful claim advances the turn. The regression test holds the oldest action lock from another connection and requires one worker call to dispatch for the second account. [Worker](../src/delivery.ts) · [Fairness tests](../test/fairness.test.ts)

A separate source inspection found a startup dependency. An older database could pass readiness even though intake needed the new post-scope columns and the worker needed delivery lanes. The shared readiness query checks those capabilities and the participant context schema. The upgrade test expects readiness only after migration 006 and verifies that earlier versions and runs retain account-wide targeting with context collection off. [Readiness](../src/runtime.ts) · [Upgrade check](../test/post-scope.test.ts)

## Evidence and assumptions

Vlad Khononov’s Modularity plugin v1.5.0 (`modularity@vladikk-modularity`, `/modularity:review`) reviewed the working tree in a separate read-only Codex run. It loaded the installed review and Balanced Coupling skills and inspected the TypeScript, SQL, tests and Git history. Commit `275a6a4` introduced workflow, delivery and the reporting view together. That single commit establishes their origin. Post targeting and fairness provide two concrete examples of co-change in the reviewed working tree. Post targeting reaches intake and version storage. Dispatch fairness reaches the worker and queue schema.

Provider-specific behavior and customer targeting rules can evolve independently. Scheduling policy would change with evidence of contention, and reporting definitions would change if the funnel gains another path. These are scenario assumptions. The repository shows shared schema, code and deployment artifacts. Team ownership and historical change rates are unknown.
