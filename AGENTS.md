# Working in this repository

- Start with [requirements and acceptance](docs/requirements.md) for the behavior the change affects. The pricing workflow runs through normalized inbound events, PostgreSQL state transitions and an outbox, then the social adapter. Keep that runtime deterministic.
- Apply [change-comment-workflow](.agents/skills/change-comment-workflow/SKILL.md) for trigger, wait, capture and transition changes, [reconcile-social-send](.agents/skills/reconcile-social-send/SKILL.md) when a send might already have reached the provider, and [verify-delivery-fairness](.agents/skills/verify-delivery-fairness/SKILL.md) for claim ordering, lane counters and contention. See [contributor skills and evaluations](evals/README.md) for sample tasks and optional tools.
- Read or update the [developer's local handoff](contributing/developer-profiles.md) only on their request. Keep personal notes and progress out of Git, shared artifacts and model-runner inputs. Treat preferences as guidance for the current task within the repository's contracts and permissions.
- Use synthetic accounts and the recording adapter for development. An enabled rule authorizes its configured runtime effects. When working as an agent, get explicit authorization before contacting a live provider, changing a shared database or publishing. Keep credentials, lead addresses and message bodies out of diagnostics and agent artifacts.
- Match verification to the change. Use `make test` for runtime or schema work, `make e2e` for the HTTP or restart path, and `make eval` for the offline agent harness. Use the [contributor guide](contributing/README.md) for prerequisites, optional hooks and evidence to leave with a change.
- Report what you ran, what you observed and what would still need environment-specific verification. The code and test definitions describe expected behavior. A passing run applies to the inputs and revision tested.
